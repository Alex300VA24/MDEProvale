PROMPT DE IMPLEMENTACIÓN — REPORTES PVL CON BLADE + GEMINI + RAG

Este archivo no es solo documentación. Debes tratarlo como la especificación/prompt principal para implementar esta funcionalidad dentro del proyecto Laravel existente.

0. Objetivo general

Implementa en el proyecto existente una funcionalidad denominada, de preferencia, Generación Inteligente de Reportes PVL, capaz de generar automáticamente los siguientes documentos oficiales del Programa del Vaso de Leche:

ANEXO N.° 1 — FORMATO PVL
Información mensual de gastos e ingresos del Programa del Vaso de Leche.

ANEXO N.° 2 — FORMATO RACIÓN A
Informe de la ración distribuida por el Programa del Vaso de Leche.

Las plantillas Blade ya están creadas y deben ser la base visual permanente de los documentos. La IA NO debe diseñar ni reconstruir los formularios. Gemini debe utilizarse para analizar, recuperar, relacionar y estructurar información; el backend debe validar y calcular; Blade debe renderizar; DOMPDF debe generar el PDF.

Arquitectura objetivo:

BASE DE DATOS DEL SISTEMA
          +
DOCUMENTOS / ARCHIVOS DEL PVL
          ↓
     RECUPERACIÓN RAG
          ↓
        GEMINI
          ↓
 JSON ESTRUCTURADO + TRAZABILIDAD
          ↓
 VALIDACIONES Y CÁLCULOS EN LARAVEL
          ↓
  PLANTILLA BLADE OFICIAL
          ↓
        DOMPDF
          ↓
         PDF

1. REGLAS OBLIGATORIAS PARA TRABAJAR SOBRE EL PROYECTO

Antes de modificar código:

Analiza la estructura actual del proyecto Laravel.

Identifica las versiones de PHP y Laravel.

Identifica los modelos, migraciones, tablas, controladores, servicios, repositorios y rutas ya existentes relacionados con:

beneficiarios;

comités/asociaciones;

productos/alimentos;

proveedores;

compras;

comprobantes/facturas;

entregas/distribuciones;

inventario/stock;

responsables;

documentos/archivos;

periodos/meses;

configuración de Gemini.

Gemini ya está configurado en el proyecto. No reemplaces ni dupliques la configuración existente. Localiza el cliente, servicio, facade, provider o wrapper actual y reutilízalo.

No escribas API keys en código, vistas, controladores, migraciones ni README.

No elimines funcionalidades existentes para adaptar esta implementación.

Reutiliza convenciones y patrones arquitectónicos ya presentes en el proyecto.

Si ya existe infraestructura de IA, embeddings, vector store, búsqueda semántica, almacenamiento documental o colas, reutilízala.

Si algún componente necesario no existe, créalo de manera modular y desacoplada.

No inventes nombres de tablas o columnas sin revisar primero el proyecto. Adapta los mapeos a la estructura real encontrada.

2. ARCHIVOS BLADE YA DISPONIBLES

Integra las plantillas entregadas en estas rutas:

resources/views/reportes/pvl/formato.blade.php
resources/views/reportes/racion/formato.blade.php

También existe el servicio base:

app/Services/ReportePvlPdfService.php

La intención es conservar estas vistas como plantillas maestras.

Regla crítica

NO permitas que Gemini modifique el HTML, CSS o Blade de estas plantillas durante la generación de cada informe.

Gemini únicamente debe producir datos estructurados.

La plantilla es fija; los valores son dinámicos.

Solo modifica estas vistas si es estrictamente necesario para corregir compatibilidad con el proyecto o para completar un campo oficial faltante. No alteres arbitrariamente:

encabezados;

títulos;

nombre del anexo;

numeración de campos;

estructura de tablas;

espacios para firma y sello;

orientación;

cantidad esperada de páginas;

distribución visual general.

3. GENERACIÓN DE PDF

Utiliza barryvdh/laravel-dompdf si el proyecto ya lo tiene o si no existe otro motor PDF equivalente instalado.

Instalación solo si es necesaria:

composer require barryvdh/laravel-dompdf

El servicio base ya contempla:

Pdf::loadView('reportes.pvl.formato', compact('data'))
    ->setPaper('a4', 'landscape');

para el Formato PVL y:

Pdf::loadView('reportes.racion.formato', compact('data'))
    ->setPaper('a4', 'portrait');

para Ración A.

No generes el PDF escribiendo coordenadas manualmente sobre el PDF original. El documento final debe salir desde las plantillas Blade.

4. RESPONSABILIDAD DE GEMINI

Gemini debe actuar como agente de análisis documental y estructuración, no como calculadora financiera ni como generador libre de documentos.

Gemini debe:

comprender documentos recuperados por RAG;

identificar valores asociados a campos oficiales;

relacionar documentos con compras, productos, lotes, certificados, periodos y entregas;

resolver variaciones de redacción de nombres;

extraer información relevante de documentos;

indicar de qué fuente obtuvo cada dato;

detectar contradicciones entre fuentes;

devolver exclusivamente una estructura JSON controlada;

marcar datos faltantes;

aportar observaciones y nivel de confianza cuando corresponda.

Gemini NO debe:

inventar valores;

estimar datos faltantes;

asumir que compra y distribución ocurren en el mismo mes;

inventar códigos de envío;

inventar números de expediente;

calcular totales que el backend pueda calcular de forma determinística;

decidir silenciosamente entre dos fuentes contradictorias;

modificar las plantillas Blade;

devolver HTML para reemplazar las plantillas;

introducir texto explicativo dentro del PDF oficial.

5. PRIORIDAD DE FUENTES

Aplica esta prioridad general:

1. Datos estructurados y confirmados de la base de datos.
2. Documentos oficiales almacenados en el sistema y recuperados mediante RAG.
3. Datos ingresados expresamente por un usuario autorizado.
4. Valores calculados determinísticamente por el backend.

Cuando la base de datos y un documento entren en conflicto, no sobrescribas silenciosamente un dato. Genera una inconsistencia para revisión.

Los documentos pueden complementar campos que no existan estructurados en la BD, por ejemplo:

certificados bromatológicos;

certificados microbiológicos;

número de lote;

fecha de vencimiento;

composición porcentual;

fichas técnicas;

documentos de entrega;

detalles de comprobantes;

referencias documentales.

6. RAG — RECUPERACIÓN AUMENTADA POR GENERACIÓN

Implementa o reutiliza una capa RAG real.

6.1 Indexación

Los documentos del PVL deben poder indexarse con metadatos suficientes para filtrar antes de la búsqueda semántica. Como mínimo, cuando sea posible, conserva:

{
  "document_id": 123,
  "tipo_documento": "certificado_calidad",
  "periodo": "2026-06",
  "producto_id": 8,
  "proveedor_id": 3,
  "nombre_archivo": "certificado_junio.pdf",
  "pagina": 1,
  "chunk": 4
}

No todos los metadatos serán obligatorios para todos los documentos; utiliza null cuando no aplique.

6.2 Fragmentación

Divide documentos en fragmentos adecuados para recuperación. Evita mandar todos los archivos del sistema a Gemini en cada solicitud.

Cada fragmento debe mantener trazabilidad hacia:

documento;

página si está disponible;

tipo de documento;

periodo;

entidad relacionada, si se puede determinar.

6.3 Embeddings y búsqueda

Si el proyecto ya tiene embeddings/vector store, reutilízalo.

Si no existe, implementa la solución que mejor encaje con la infraestructura actual. Si la integración Gemini configurada admite embeddings, puede utilizarse un modelo de embeddings de Gemini compatible con la configuración existente. No cambies de proveedor de IA sin necesidad.

La búsqueda debe combinar, cuando sea posible:

filtros estructurados por periodo/tipo/producto;

recuperación semántica;

límite de resultados relevantes;

metadatos de trazabilidad.

6.4 Consultas RAG sugeridas

Para el Formato PVL, recuperar principalmente información relacionada con:

facturas/comprobantes;

proveedores;

órdenes de compra;

alimentos equivalentes;

insumos complementarios;

donaciones;

movimientos financieros;

transferencias;

responsables administrativos.

Para Ración A, recuperar principalmente:

hojas de distribución/entrega;

certificados físico-químicos/bromatológicos;

certificados microbiológicos;

fichas técnicas;

lotes;

vencimientos;

composición del alimento;

datos de atención;

responsables;

documentos relacionados con beneficiarios y comités cuando aplique.

7. FLUJO FUNCIONAL

Implementa el flujo siguiente.

Paso 1 — Solicitud

El usuario selecciona al menos:

- tipo de reporte: PVL | RACION_A | AMBOS
- mes
- año

Opcionalmente puede seleccionar municipalidad si el sistema es multi-municipalidad.

Paso 2 — Contexto estructurado

Laravel consulta la BD y obtiene toda la información estructurada disponible para ese periodo.

Paso 3 — Recuperación RAG

Busca únicamente documentos relevantes para el periodo y las entidades involucradas.

Paso 4 — Gemini

Envía a Gemini:

el objetivo del reporte;

el esquema JSON esperado;

datos estructurados relevantes;

fragmentos recuperados mediante RAG;

instrucciones estrictas de no inventar;

obligación de incluir trazabilidad.

Paso 5 — Respuesta estructurada

Gemini debe devolver JSON válido. No debe devolver Markdown, bloques de código ni prosa adicional cuando la ejecución sea para generación automática.

Paso 6 — Validación en Laravel

Valida:

tipos de dato;

campos obligatorios;

fórmulas;

duplicados;

continuidad financiera;

coherencia temporal;

composición;

beneficiarios;

procedencia de los datos.

Paso 7 — Vista previa

Antes de descargar el PDF, la interfaz debe poder mostrar al usuario:

Estado: LISTO PARA GENERAR / REQUIERE REVISIÓN
Datos encontrados
Datos faltantes
Advertencias
Errores críticos
Fuentes utilizadas

Paso 8 — Generación

Solo cuando no existan errores críticos, transforma el resultado validado al $data esperado por la plantilla Blade correspondiente y genera el PDF.

11. TRAZABILIDAD RAG

Cada valor obtenido de documentos debe poder rastrearse.

Ejemplo:

{
  "campo": "certificados.0.numero_certificado",
  "valor": "612-2026, 611-2026",
  "origen": "RAG",
  "document_id": 412,
  "archivo": "certificado_calidad_junio.pdf",
  "pagina": 1,
  "chunk": 3,
  "confianza": 0.97
}

Para datos provenientes de BD:

{
  "campo": "beneficiarios.urbana.total",
  "valor": 3872,
  "origen": "BD",
  "entidad": "beneficiarios",
  "referencia": "consulta del periodo 2026-06"
}

La trazabilidad se muestra en la interfaz administrativa, no dentro del PDF oficial.

12. MANEJO DE CONFLICTOS

Si dos fuentes contienen valores distintos para el mismo campo, Gemini debe devolver ambos.

Ejemplo:

{
  "campo": "certificados.0.numero_lote",
  "tipo": "CONFLICTO_FUENTES",
  "opciones": [
    {
      "valor": "002",
      "document_id": 10
    },
    {
      "valor": "003",
      "document_id": 12
    }
  ]
}

El backend debe marcar el reporte como REQUIERE_REVISION hasta que el conflicto sea resuelto.

Nunca le pidas a Gemini que “elija el más probable” sin evidencia suficiente.

13. VALIDACIONES DETERMINÍSTICAS DEL BACKEND

Estas validaciones deben implementarse en PHP/Laravel y no depender únicamente de Gemini.

13.1 Formato PVL

Total de compras de alimentos

total_compras_alimentos = suma(importe de compras_alimentos)

Total de insumos

total_compras_insumos = suma(importe de compras_insumos)

Total de donaciones valorizadas

total_donaciones = suma(importe de donaciones)

Total de gastos

Respeta la estructura real del sistema y formulario. Como regla general:

total_gastos = total_compras_alimentos
             + total_compras_insumos
             + total_gastos_operativos

No sumes dos veces las donaciones si no constituyen gasto presupuestal según los datos reales del sistema.

Total de recursos

total_recursos = saldo_inicial_tesoro
               + transferencia_tesoro
               + recursos_directamente_recaudados
               + foncomun
               + donaciones
               + intereses

Saldo final

saldo_final = total_recursos - total_gastos

Un saldo final negativo es posible; no lo conviertas automáticamente a cero.

Continuidad mensual

Cuando exista el mes anterior:

saldo_final_mes_anterior == saldo_inicial_tesoro_mes_actual

Si difiere, genera advertencia o error según la regla de negocio que se defina.

13.2 Beneficiarios

Calcula por separado:

total_rural = suma de las 8 categorías rurales
total_urbana = suma de las 8 categorías urbanas

Compara con los totales recibidos.

13.3 Composición

Por cada producto compuesto:

suma(porcentajes) ≈ 100

Permite una tolerancia pequeña por redondeo configurable.

13.4 Certificados

Verifica cuando existan fechas confiables:

fecha_vencimiento >= fecha_distribucion

Marca como crítico un producto distribuido con lote vencido.

13.5 Duplicidad de comprobantes

Detecta duplicados por una combinación equivalente a:

RUC + tipo_comprobante + serie + numero_comprobante

13.6 Compra vs. distribución

No asumir:

comprado_en_mes == distribuido_en_mes

Un producto comprado en un mes puede ser utilizado en el siguiente.

Cuando exista inventario, usa una conciliación equivalente a:

stock_inicial + entradas - salidas = stock_final

14. SEVERIDAD DE HALLAZGOS

Implementa al menos:

CRITICO
ADVERTENCIA
INFORMATIVO

Ejemplos:

CRÍTICO

campo obligatorio sin fuente;

factura duplicada con impacto en totales;

lote vencido durante la distribución;

conflicto sin resolver en un valor obligatorio;

total financiero inconsistente;

documento generado con información perteneciente a otro periodo.

ADVERTENCIA

saldo inicial no coincide con mes anterior;

certificado próximo a vencer;

documento de respaldo incompleto;

código de expediente vacío si el negocio permite continuar.

INFORMATIVO

campo opcional no disponible;

valor obtenido exclusivamente desde una fuente documental;

ausencia confirmada de registros en una sección.

15. PROMPT INTERNO PARA GEMINI

No distribuyas lógica crítica por múltiples prompts difíciles de mantener. Crea un servicio/clase central que componga un prompt similar al siguiente, adaptándolo al cliente Gemini que ya existe:

Eres el agente de extracción y conciliación documental del Programa del Vaso de Leche.

Tu tarea es producir datos estructurados para el reporte solicitado.

REGLAS:
1. No inventes ningún dato.
2. Usa primero la información estructurada proporcionada por el backend.
3. Usa los fragmentos RAG únicamente para complementar o contrastar esa información.
4. Si un valor no está disponible, usa null.
5. No calcules totales financieros finales; el backend los recalculará.
6. No generes HTML, Blade ni PDF.
7. No modifiques títulos o estructura del formato.
8. No supongas que una compra se distribuye en el mismo mes.
9. Si dos fuentes discrepan, registra un conflicto.
10. Devuelve JSON válido y nada más.
11. Conserva trazabilidad para cada dato documental.
12. Nunca uses conocimiento general para completar un campo administrativo que no aparezca en las fuentes.

TIPO DE REPORTE:
{{tipo_reporte}}

PERIODO:
{{periodo}}

DATOS ESTRUCTURADOS DEL SISTEMA:
{{datos_bd}}

CONTEXTO RAG:
{{fragmentos_rag}}

ESQUEMA DE SALIDA:
{{json_schema}}

Si la librería/SDK actual de Gemini permite structured output / JSON schema / response schema, utilízalo en lugar de depender solo de instrucciones textuales.

Configura temperatura baja para esta tarea de extracción si la integración existente permite ese parámetro.

16. SERVICIOS RECOMENDADOS

No es obligatorio usar exactamente estos nombres si el proyecto tiene otra arquitectura, pero la separación de responsabilidades sí debe mantenerse.

app/Services/Pvl/
    PvlReportContextService.php
    PvlRagService.php
    PvlGeminiReportService.php
    PvlReportValidationService.php
    PvlReportDataMapper.php
    PvlReportGeneratorService.php

Responsabilidad sugerida:

PvlReportContextService

Obtiene datos estructurados de BD para mes/año.

PvlRagService

Indexa, busca y devuelve fragmentos documentales relevantes.

PvlGeminiReportService

Invoca la integración Gemini ya existente y devuelve el JSON analizado.

PvlReportValidationService

Recalcula y valida todos los datos determinísticos.

PvlReportDataMapper

Convierte la estructura interna validada al array $data exacto que espera cada Blade.

PvlReportGeneratorService

Orquesta el proceso y delega la generación del PDF a ReportePvlPdfService.

Evita colocar toda la lógica en un solo controlador.

Al mapear hacia Blade, decide según la semántica del campo si debe mostrarse vacío. Nunca sustituyas un dato desconocido por contenido inventado.

22. FUENTE DE VERDAD Y AUTORIZACIÓN HUMANA

Gemini no es la autoridad final.

Gemini propone/extracta
        ↓
Laravel valida
        ↓
Usuario revisa cuando sea necesario
        ↓
Plantilla genera

Para conflictos o campos administrativos sensibles, permite corrección manual por un usuario autorizado, conservando auditoría del valor original, valor corregido y responsable de la corrección si la arquitectura del proyecto ya contempla auditoría.

si sigue fallando, muestra un error recuperable al usuario.

26. RENDIMIENTO

guarda hash del archivo para detectar duplicados.
